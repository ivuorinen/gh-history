# Issue-comment fetch failures discard already-fetched comments and warn only under --verbose

## Problem

When `FetchIssueComments` returns an error, `fetchEvents` logs it through
`logVerbose` — which prints nothing unless `--verbose` was passed — and takes the
`else` branch, throwing away the partial `comments` slice the function returned
alongside the error.

## Evidence

`main.go:125-130`:

    comments, err := client.FetchIssueComments(username, dr)
    if err != nil {
        logVerbose(cfg.verbose, "Warning: GraphQL comments error: %v", err)
    } else {
        allEvents = append(allEvents, comments...)
    }

`FetchIssueComments` deliberately returns accumulated events with the error
(client.go:633: `return events, fmt.Errorf(...)`), so the discard is a loss of data
the API already paid for.

## Impact

Two failures compound. First, a user running without `--verbose` — the default —
gets no indication whatsoever that comment fetching failed; the report simply
contains zero comments and looks complete. Second, if the failure happens on page 7
of 10, the six successfully-fetched pages are dropped as well, so even a
`--verbose` user loses data that was retrieved successfully.

## Fix

Keep the partial data and make the warning unconditional — a degraded result the
user cannot see is worse than no result:

    comments, err := client.FetchIssueComments(username, dr)
    if len(comments) > 0 {
        allEvents = append(allEvents, comments...)
    }
    if err != nil {
        fmt.Fprintf(os.Stderr, "Warning: issue comments incomplete: %v\n", err)
    }

The same pattern applies to any other partial-result path added later: append what
succeeded, warn on stderr regardless of verbosity.
